## Release

### Minimising SmartScreen warnings (Microsoft)

#### Minimizing SmartScreen warnings in practice

- DEVIATION **SS-1** Publish to the Microsoft Store where feasible: this is the most reliable way to avoid warnings entirely
  - Not listing in the Microsoft Store (decided 8 October 2026). SmartScreen reputation comes from signing every release with one identity (SS-2, SS-5). Without a storefront there is no IARC rating, since IARC is reached only through a participating store; the age floor (PRIV-1) is stated by the project instead.
- [ ] **SS-2** Sign every release: unsigned files cannot inherit a positive reputation from the signing certificate
  - [ ] Sign the launcher and the client on every release (plan item M3). Unsigned, Smart App Control can block the client outright (seen in Windows Sandbox, 5 October 2026).
- [ ] **SS-3** Do not modify signed files - Avoid modifying files after signing as doing so can break the signature depending on client configuration
  - [ ] Release order: build, sign, then zip, then compute the SHA-256. Nothing is patched after signing; the client's binary patches happen before.
- [ ] **SS-4** Do not sign potentially unwanted applications - Avoid signing any file which exhibits malicious or potentially unwanted application behavior, or the certificate may develop negative reputation
  - [ ] The launcher behaves like an ordinary program: no bundled extras, no autostart, no elevation, nothing written outside its folder (REL-1).
- [ ] **SS-5** Use a consistent signing identity: changing your signing certificate affects the publisher trust signal
  - [ ] One signing identity for every release; record it here once chosen.
- [ ] **SS-6** Communicate with early adopters: for new apps, let beta users know they may see a SmartScreen prompt on first download, and that they should only proceed after verifying the publisher and confirming they trust the download source
  - [x] The download page warns about the unrecognised publisher.
  - [ ] Add what Smart App Control does and what to do (Website_Checklist R9).

### Attacks on software update (The Update Framework)

#### Arbitrary installation attacks

- [ ] **TUF-1** An attacker cannot install anything they want on the client system. That is, an attacker cannot provide arbitrary files in response to download requests.
  - The launcher does not update itself: the player downloads a new zip from the release page (one-click update was removed, plan item L3).
  - [ ] The download page publishes the SHA-256 of each zip and explains how to check it (Website_Checklist R8).
  - [ ] Signed builds (M3) make a replaced file detectable by Windows itself.

#### Endless data attacks

- [ ] **TUF-2** An attacker cannot respond to client requests with huge amounts of data (extremely large files) that interfere with the client's system.
  - The launcher does download turns and notes from the relay and Storage.
  - [ ] The launcher caps the size of a turn, note or answer it will read, and stops reading past it.

#### Extraneous dependencies attacks

- N/A **TUF-3** An attacker cannot cause clients to download or install software dependencies that are not the intended dependencies.
  - N/A: The launcher does not update itself: the player downloads a new zip from the release page (one-click update was removed, plan item L3). No dependencies are fetched at run time.

#### Fast-forward attacks

- N/A **TUF-4** An attacker cannot arbitrarily increase the version numbers of metadata files, listed in the snapshot metadata, well beyond the current value and thus tricking a software update system into thinking any subsequent updates are trying to rollback the package to a previous, out-of-date version. In some situations, such as those where there is a maximum possible version number, the perpetrator cannot use a number so high that the system would never be able to match it with the one in the snapshot metadata, and thus new updates could never be downloaded.
  - N/A: The launcher does not update itself: the player downloads a new zip from the release page (one-click update was removed, plan item L3).

#### Indefinite freeze attacks

- [ ] **TUF-5** An attacker cannot respond to client requests with the same, outdated metadata without the client being aware of the problem.
  - The analogue here is turns: a launcher served the same old turn must notice.
  - [ ] Multiplayer_Checklist M8: a turn the launcher could not refresh is labelled with its age.

#### Malicious mirrors preventing updates

- N/A **TUF-6** A repository mirror cannot prevent updates from good mirrors.
  - N/A: No mirrors. One release page (GitHub) and one relay.

#### Mix-and-match attacks

- N/A **TUF-7** An attacker cannot trick clients into using a combination of metadata that never existed together on the repository at the same time.
  - N/A: The launcher does not update itself: the player downloads a new zip from the release page (one-click update was removed, plan item L3).

#### Rollback attacks

- [ ] **TUF-8** An attacker cannot trick clients into installing software that is older than that which the client previously knew to be available.
  - [ ] The update notice never points to a build older than the one running.
  - [ ] A galaxy's `min_build` only rises.

#### Vulnerability to key compromises

- [ ] **TUF-9** An attacker, who is able to compromise a single key or less than a given threshold of keys, cannot compromise clients. This includes compromising a single online key (such as only being protected by SSL) or a single offline key (such as most software update systems use to sign files).
  - [ ] The code-signing identity (M3) is the one key that vouches for every build. Keep it in a managed service (Azure Artifact Signing) behind an MFA-protected account, not as a file on the build PC.
  - [ ] The GitHub account that publishes releases has MFA.

#### Wrong software installation

- [ ] **TUF-10** An attacker cannot provide a file (trusted or untrusted) that is not the one the client wanted.
  - [ ] The update notice links one hard-coded release page, never a URL taken from the relay or a galaxy.

### Releasing the launcher (REL)

- [ ] **REL-1** The launcher installs and uninstalls cleanly: unzipping is installing, deleting the folder is uninstalling, and nothing is left behind.
  - Source: Windows Desktop App Certification Requirements v3.3 (Microsoft, 2014), requirement group 5 (clean, reversible install), paraphrased.
  - [ ] The download page says nothing is written outside the folder. Check it: where the identity file, logs, the client's files and any registry keys go.
  - [ ] If anything is written to `%APPDATA%` or the registry, the page and the uninstall note say so.
- [ ] **REL-2** The launcher runs without administrator rights, does not start with Windows, and keeps user data where a standard user can write it.
  - Source: Windows Desktop App Certification Requirements v3.3, requirement groups 9 and 10, paraphrased.
  - [ ] The launcher and the client run as `asInvoker` (no elevation prompt).
  - [ ] Unzipping into `C:\Program Files` fails for a standard user because the data folder is inside it: say so on the download page, or move user data to `%LOCALAPPDATA%`.
  - [ ] No autostart entry.
- [ ] **REL-3** Every release is reproducible from the repository and documented: version, release notes, the zip, and its SHA-256 on the release page and the download page.
  - Source: Apache "Release Download Pages for Projects"; NIST SP 800-218 SSDF practice PS (protect the software).
  - [ ] `release/build.ps1` builds from a clean checkout at a tagged commit.
  - [ ] The release notes name what changed for players.
  - [ ] The download page and the release page agree (Website_Checklist R8).
- [ ] **REL-4** Each release is checked against the antivirus engines players use, and false positives are reported to the vendor before the release is announced.
  - Source: Microsoft Security Intelligence file submission (software developer, expected "clean").
  - [ ] Submit each release to Microsoft Defender.
  - [ ] Scan with a multi-engine scanner and record the result; report false positives to each vendor that flags it.
- [ ] **REL-5** Each release passes the verification checklists that cover what changed before it is published.
  - Source: This project.
  - [ ] Singleplayer_UI_Checklist for the client and the launcher's single-player path.
  - [ ] Multiplayer_Checklist M items for joining and playing a turn against a live galaxy.
  - [ ] Security_Checklist items that name the launcher.
- [ ] **REL-6** A signing option is chosen that the operator can actually enrol in.
  - Source: Microsoft Learn, "Code signing options for Windows app developers" (29 August 2026).
  - [ ] Azure Artifact Signing (about $9.99 a month) accepts individuals in the USA and Canada only; check the operator's eligibility.
  - [ ] Record the choice in plan item M3.

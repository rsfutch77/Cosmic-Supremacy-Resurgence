## Release

### Minimising SmartScreen warnings (Microsoft)

#### Minimizing SmartScreen warnings in practice

- DEVIATION **SS-1** Publish to the Microsoft Store where feasible: this is the most reliable way to avoid warnings entirely
  - Not listing in the Microsoft Store (decided 8 October 2026). SmartScreen reputation comes from signing every release with one identity (SS-2, SS-5). Without a storefront there is no IARC rating, since IARC is reached only through a participating store; the age floor (PRIV-1) is stated by the project instead.
- [x] **SS-2** Sign every release: unsigned files cannot inherit a positive reputation from the signing certificate
  - [x] Sign the launcher and the client on every release. Unsigned, Smart App Control can block the client outright (seen in Windows Sandbox, 5 October 2026). v0.8.0: all five exes read back Valid, signed by CN=Robert Futch and timestamped (25 November 2026).
- [x] **SS-3** Do not modify signed files - Avoid modifying files after signing as doing so can break the signature depending on client configuration
  - [x] Release order: build, sign, then zip, then compute the SHA-256. Nothing is patched after signing; the client's binary patches happen before. `build.ps1` patches the clients as it stages them, signs, then zips and hashes (v0.8.0 build log, 25 November 2026).
- [ ] **SS-4** Do not sign potentially unwanted applications - Avoid signing any file which exhibits malicious or potentially unwanted application behavior, or the certificate may develop negative reputation
  - [ ] The launcher behaves like an ordinary program: no bundled extras, no autostart, no elevation, nothing written outside its folder (REL-1). No autostart and no elevation (REL-2). Two exceptions stand: the zip carries Microsoft's WebView2 bootstrapper, run only when the runtime is missing, and the client writes `HKCU\Software\CosmicSupremacy` (REL-1).
  - [x] The updater keeps to the same rules: no elevation, nothing written outside the launcher's folder. It stages under `update\` beside the launcher and never touches `data\` (`release/updater.py`, `test_updater`).
- [x] **SS-5** Use a consistent signing identity: changing your signing certificate affects the publisher trust signal
  - [x] One signing identity for every release; record it here once chosen. Azure Artifact Signing, subject `CN=Robert Futch, O=Robert Futch, L=Tucson, S=az, C=US`, pinned in `updater.SIGNER_SUBJECT` with its issuer and EKU.
- [x] **SS-6** Communicate with early adopters: for new apps, let beta users know they may see a SmartScreen prompt on first download, and that they should only proceed after verifying the publisher and confirming they trust the download source
  - [x] The download page warns about the unrecognised publisher.
  - [x] It also says to check that the publisher is Robert Futch before clicking Run anyway, and that Smart App Control need not be turned off (Website_Checklist R9).

### Attacks on software update (The Update Framework)

#### Arbitrary installation attacks

- [x] **TUF-1** An attacker cannot install anything they want on the client system. That is, an attacker cannot provide arbitrary files in response to download requests.
  - The launcher updates itself (`release/updater.py`); a player can also download the zip from the release page.
  - [x] The download page publishes the SHA-256 of each zip and explains how to check it (Website_Checklist R8).
  - [x] Signed builds (M3) make a replaced file detectable by Windows itself.
  - [x] The updater installs only a build signed by the project's identity (SS-5) whose SHA-256 matches the one the release publishes. It also needs the SHA-256 in the release notes to match the asset's digest, so the notes must carry it before `gh release create`.

#### Endless data attacks

- [ ] **TUF-2** An attacker cannot respond to client requests with huge amounts of data (extremely large files) that interfere with the client's system.
  - The launcher downloads turns and notes from the relay and Storage, and releases from the release page.
  - [ ] The launcher caps the size of a turn, note or answer it will read, and stops reading past it. Open: `HttpTurnStore._get` and the relay calls in `launcher.py` read whole answers; only the news, its picture and the release listing are capped.
  - [x] The updater stops a download that runs past the size the release lists (`updater.download`, and no zip over `MAX_ZIP`).

#### Extraneous dependencies attacks

- [x] **TUF-3** An attacker cannot cause clients to download or install software dependencies that are not the intended dependencies.
  - The launcher updates itself (`release/updater.py`); a player can also download the zip from the release page.
  - [x] An update is one signed zip. The updater fetches no dependencies or plug-ins, at update time or at run time.

#### Fast-forward attacks

- [x] **TUF-4** An attacker cannot arbitrarily increase the version numbers of metadata files, listed in the snapshot metadata, well beyond the current value and thus tricking a software update system into thinking any subsequent updates are trying to rollback the package to a previous, out-of-date version. In some situations, such as those where there is a maximum possible version number, the perpetrator cannot use a number so high that the system would never be able to match it with the one in the snapshot metadata, and thus new updates could never be downloaded.
  - The launcher updates itself (`release/updater.py`); a player can also download the zip from the release page.
  - [x] The updater remembers only a version it read from a verified build, so an inflated number in the release listing cannot block later updates. It keeps no version at all: each check compares the listing with the running build, and installs only if the staged build's own stamp is newer.

#### Indefinite freeze attacks

- [ ] **TUF-5** An attacker cannot respond to client requests with the same, outdated metadata without the client being aware of the problem.
  - The analogue here is turns: a launcher served the same old turn must notice.
  - [ ] Multiplayer_Checklist M8: a turn the launcher could not refresh is labelled with its age.
  - [x] An update check that could not reach the release page says so, rather than "up to date" (`test_updater`).

#### Malicious mirrors preventing updates

- N/A **TUF-6** A repository mirror cannot prevent updates from good mirrors.
  - N/A: No mirrors. One release page (GitHub) and one relay.

#### Mix-and-match attacks

- [x] **TUF-7** An attacker cannot trick clients into using a combination of metadata that never existed together on the repository at the same time.
  - The launcher updates itself (`release/updater.py`); a player can also download the zip from the release page.
  - [x] The version, the zip and its SHA-256 all come from one release, never combined across releases. The zip must be offered under that release's tag.

#### Rollback attacks

- [x] **TUF-8** An attacker cannot trick clients into installing software that is older than that which the client previously knew to be available.
  - [x] The update notice never points to a build older than the one running (`updater.is_newer`).
  - [x] The updater never installs a build older than the one running. It checks the staged build's own stamp, not the listing.
  - [x] A galaxy's `min_build` only rises. `galaxy_tool.set_min_build` refuses a lower one.

#### Vulnerability to key compromises

- [x] **TUF-9** An attacker, who is able to compromise a single key or less than a given threshold of keys, cannot compromise clients. This includes compromising a single online key (such as only being protected by SSL) or a single offline key (such as most software update systems use to sign files).
  - [x] The code-signing identity (M3) is the one key that vouches for every build. Keep it in a managed service (Azure Artifact Signing) behind an MFA-protected account, not as a file on the build PC. The key is in Azure Artifact Signing, with no file on the build PC, and the Azure sign-in that signed v0.8.0 used MFA (its token lists `mfa`, 26 November 2026).
  - [x] The GitHub account that publishes releases has MFA. Two-factor is on (Robert, 26 November 2026).
  - [x] The updater trusts the signing identity, not the download host, so a compromised GitHub account alone cannot ship a build the launcher installs.

#### Wrong software installation

- [x] **TUF-10** An attacker cannot provide a file (trusted or untrusted) that is not the one the client wanted.
  - [x] The update notice and the updater use one hard-coded release page, never a URL taken from the relay or a galaxy (`updater.FEED`, `launcher.UPDATE_URL`).

### Releasing the launcher (REL)

- [ ] **REL-1** The launcher installs and uninstalls cleanly: unzipping is installing, deleting the folder is uninstalling, and nothing is left behind.
  - Source: Windows Desktop App Certification Requirements v3.3 (Microsoft, 2014), requirement group 5 (clean, reversible install), paraphrased.
  - [x] The download page says nothing is written outside the folder. Check it: where the identity file, logs, the client's files and any registry keys go. Checked 25 November 2026: the identity file and logs stay in `data\`, but the client writes `HKCU\Software\CosmicSupremacy` (window positions and proxy settings), and `data\` falls back to `%LOCALAPPDATA%\CosmicSupremacyResurgence` when the folder is not writable. The page names both since the v0.8.0 deploy.
  - [x] If anything is written to `%APPDATA%` or the registry, the page and the uninstall note say so. The uninstall note names the registry key and the `%LOCALAPPDATA%` folder (live 26 November 2026).
- [ ] **REL-2** The launcher runs without administrator rights, does not start with Windows, and keeps user data where a standard user can write it.
  - Source: Windows Desktop App Certification Requirements v3.3, requirement groups 9 and 10, paraphrased.
  - [x] The launcher and the client run as `asInvoker` (no elevation prompt). The release tests started every client unattended, and the click-through raised no prompt (25 November 2026).
  - [x] Unzipping into `C:\Program Files` fails for a standard user because the data folder is inside it: say so on the download page, or move user data to `%LOCALAPPDATA%`. The launcher moves `data\` to `%LOCALAPPDATA%\CosmicSupremacyResurgence` when its folder is not writable.
  - [x] No autostart entry.
- [ ] **REL-3** Every release is reproducible from the repository and documented: version, release notes, the zip, and its SHA-256 on the release page and the download page.
  - Source: Apache "Release Download Pages for Projects"; NIST SP 800-218 SSDF practice PS (protect the software).
  - [x] `release/build.ps1` builds from a clean checkout at a tagged commit. v0.8.0 from a worktree at the tag, stamped `9ef557b` with no `+` (25 November 2026).
  - [x] The release notes name what changed for players (`release/RELEASE_NOTES_v0.8.0.md`).
  - [x] The download page and the release page agree (Website_Checklist R8). v0.8.0: the same zip, size and SHA-256 on both, and the release asset's digest matches (26 November 2026).
- [ ] **REL-4** Each release is checked against the antivirus engines players use, and false positives are reported to the vendor before the release is announced.
  - Source: Microsoft Security Intelligence file submission (software developer, expected "clean").
  - [x] Submit each release to Microsoft Defender. v0.8.0: the whole zip submitted as a software developer, as clean, on 26 November 2026; Microsoft's verdict was pending when recorded.
  - [x] Scan with a multi-engine scanner and record the result; report false positives to each vendor that flags it. v0.8.0 on VirusTotal, 26 November 2026: 0 of 44 engines flagged the zip, 22 timed out, and 7 could not read a zip. VirusTotal does not scan the files inside a zip this size, so the five exes were not scanned on their own.
  - [ ] Scan each exe on its own through VirusTotal's API, since the zip is too big for the site to scan the files inside it. Check whether the free public API's limits and terms fit a release run before scripting it.
- [ ] **REL-5** Each release passes the verification checklists that cover what changed before it is published.
  - Source: This project.
  - [ ] Singleplayer_UI_Checklist for the client and the launcher's single-player path.
  - [ ] Multiplayer_Checklist M items for joining and playing a turn against a live galaxy.
  - [ ] Security_Checklist items that name the launcher.
- [ ] **REL-6** A signing option is chosen that the operator can actually enrol in.
  - Source: Microsoft Learn, "Code signing options for Windows app developers" (29 August 2026).
  - [x] Azure Artifact Signing (about $9.99 a month) accepts individuals in the USA and Canada only; check the operator's eligibility. Robert is enrolled and has signed every release since v0.7.0.
  - [x] Record the choice in `docs/DEVELOPMENT.md` under Building a release (Release checklist step 3).
- [ ] **REL-7** The live referee runs the released code. The sandbox runs a staged copy, so a release that is not restaged leaves the referee on the old merge rules.
  - Source: This project.
  - [x] The referee is restaged from the tag with `server\sandbox\stage.ps1` and restarted between turns (`docs/DEVELOPMENT.md`, Release checklist step 10). v0.8.0 staged as `9ef557b` and the sandbox restarted at 23:56 on 25 November 2026, between turns.
  - [x] `C:\CSReferee\out\bootstrap.log` names the tag's commit, with no `+`, and the next turn closes under it. It says `stage commit 9ef557b`, and the sandbox galaxy published turn 235 under it at 01:47 on 26 November 2026.

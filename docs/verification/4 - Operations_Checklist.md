### Firebase launch checklist

#### General best practices for releasing

- [ ] **FB-GBPF-1** Make sure that you've tested all your changes in the Firebase Local Emulator Suite (for supported products) before deploying to production. Thorough testing can help prevent costly mistakes.
  - [x] The relay and the stores run against the Local Emulator Suite in their tests (`functions/emulators.py`).
  - [ ] Every relay deploy is preceded by the relay and store test suites (`functions/deploy.py` could refuse to deploy when they fail).
- [ ] **FB-GBPF-2** Start enforcing Firebase App Check for every service that supports it. App Check helps to ensure only your actual apps can access your backend services and resources.
  - [ ] Evaluate App Check for the relay. A desktop app has no platform attestation provider; the custom-provider route needs a secret in the launcher, which a player can extract. Record the decision either way.
- [x] **FB-GBPF-3** Review Firebase's general security checklist.
  - Reviewed in `docs/verification/private/Security_Checklist.md` (ASVS and GSF, with the Firebase security checklist as a supplement).
- N/A **FB-GBPF-4** Use Firebase Remote Config rollouts to safely and gradually release new features and updates to your app.
  - N/A: No Remote Config. Feature rollout is per galaxy and per build (the `min_build` gate).
- N/A **FB-GBPF-5** If you haven't already, consider setting up Firebase Crashlytics. This is a lightweight, realtime crash reporter that helps you track, prioritize, and fix stability issues that erode your app quality.
  - N/A: Crashlytics has no desktop Python SDK. Crash reports are the launcher logs sent on request, and the client's minidumps.

#### Know your pricing plan limits and set budget alerts

- [x] **FB-KYPP-1** Make sure you don't hit usage limits and quotas after going to production, especially if you're on the no-cost Spark plan. Consider upgrading to the pay-as-you-go Blaze pricing plan.
  - The project is on the Blaze plan (relay deploy requires it).
- [ ] **FB-KYPP-2** Set up budget alerts for your project.
  - [ ] Confirm a budget with alert thresholds exists on the billing account, and who receives the alerts.
- [ ] **FB-KYPP-3** Note that budget alerts are not budget caps. An alert will send you communications when you're approaching or surpassed your configured threshold so that you can take action in your app or project.
  - Noted: alerts are not caps.
- [ ] **FB-KYPP-4** Consider setting up advanced alerts and actions, like functions that will disable billing in response to alerts.
  - [x] The auto-stop-billing extension is installed (its functions are listed in the project, 7 October 2026).
  - [ ] Confirm its threshold and test what it disables: stopping billing takes the live website down with the relay.
- [ ] **FB-KYPP-5** If you use Firebase AI Logic, Firebase App Hosting, Cloud Functions for Firebase, and Firebase Extensions, we strongly recommend that you also set up spend caps, which will pause the applicable service if your project reaches the budget set for that service.
  - [x] The relay caps itself at 10 instances (`functions/main.py`).
  - [ ] Set a spend cap for Cloud Functions if the console offers one for this project.
- [ ] **FB-KYPP-6** Monitor your usage in the product-specific dashboards or in the central Usage and billing dashboard in the Firebase console.
  - [ ] Record a measured day of usage against the estimates (plan items H12, H13).

### Operating the service (OPS)

- [ ] **OPS-1** An incident process: what counts as an incident, how severe it is, who acts, how players are told, and that each serious one gets a written review.
  - Source: PagerDuty Incident Response documentation (severity levels, roles, external communication, postmortem template).
  - [ ] Define three severities: a galaxy stalled or data at risk; a feature broken for everyone; a problem for one player.
  - [ ] Where players are told: the operator page is the operator's; players need a status line in the launcher or a page on the site.
  - [ ] Postmortems: the 29 September turn-23 stall and the 5 October Smart App Control block each get a short written review.
- [ ] **OPS-2** Every live galaxy can be restored from what Firebase holds, and the restore has been tried.
  - Source: Google Cloud Well-Architected Framework, Reliability pillar, principle 8 (test data-loss recovery).
  - [x] The referee survives a reboot with its local files deleted, because the galaxy is in Firebase (plan item H3).
  - [ ] Restore a galaxy to an earlier turn from its archive on a copy, and record the steps.
  - [ ] Decide whether Firestore and Storage need backups beyond the archive (a deleted project loses both; FB-MSYF-3).
- [ ] **OPS-3** Recovery is tested, not assumed: the referee is stopped, killed and restarted on purpose and the galaxy carries on.
  - Source: Google Cloud Well-Architected Framework, Reliability pillar, principle 7 (test recovery).
  - [x] Turn 23 stall (29 September 2026): the worker retried, and the turn published once the cause was fixed.
  - [ ] A failure that repeats identically N times alerts the operator instead of retrying for hours (Security_Checklist ASVS V16.5.3).
- [ ] **OPS-4** The operator learns of a stalled galaxy without having to look.
  - Source: This project; no source covers a home PC acting as the referee.
  - [x] The operator page marks itself stale (plan item N3).
  - [ ] A push alert (email or phone) when a turn is overdue by more than one turn length.
- [ ] **OPS-5** The referee's machine is a known single point of failure, and its failure modes have a plan: power loss, ISP loss, Windows Update reboots, the operator travelling.
  - Source: This project; no source covers a home PC acting as the referee.
  - [ ] Write down what happens to each live galaxy in each case, and what players are told.
  - [ ] Move the referee to a cloud VM (the next phase) or to the Windows Sandbox once the client is signed.
- [ ] **OPS-6** The project does not depend on one person's memory: the runbook is written and someone else could follow it.
  - Source: Firebase launch checklist FB-MSYF-6 (more than one owner), extended to knowledge.
  - [ ] `docs/Public_Beta_Plan.md` "Operating it" is the runbook; check it covers starting, closing and restoring a galaxy, rebinding a seat, and deploying the relay.
- [ ] **OPS-7** Cost stays inside the budget at the target scale, with headroom.
  - Source: Firebase launch checklist FB-KYPP; plan items H9, H12, H13.
  - [ ] A measured day at beta scale, against the free-tier allowances and the budget.
